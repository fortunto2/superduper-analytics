# Метрики: что показывает панель и откуда берётся

Спека дашборда. Составлена по чужой таблице на трёх вендорах (App Store Connect + AppsFlyer +
Adapty) — но со столбцом «наш источник» вместо «наш поставщик», потому что почти всё это Apple
и мы отдаём сами.

Правило, которое действует на всю таблицу: **числа из разных источников ставятся рядом и не
складываются.** «Люди на лендинге» и «установки» считают разные стороны с разным определением
суток. Отношение между ними — воронка; сумма — бессмыслица.

## Как это хранится

| Что | Где | Почему |
|---|---|---|
| Наши события | Analytics Engine | сэмплируется, живёт 3 месяца, агрегаты только взвешенные |
| Чужие суточные итоги | D1, `store_daily` | точные, не сэмплированные, живут годами |

Одна таблица на всех поставщиков: `provider` ∈ `appstore`, `play`, `youtube`, дальше рекламные
сети. Без `CHECK` — список растёт, а `CHECK` на растущем списке это миграция на каждый канал.

## Метка кампании — одна на все каналы

Самое дешёвое сейчас и самое дорогое потом. Если словарь разъедется, ничего не сойдётся.

```
<канал>-<что именно>        youtube-nest-01 · site-hero · site-footer · tg-alina
```

Одно и то же значение подставляется в:

| Куда | Как |
|---|---|
| ссылка на App Store | `?pt=<provider>&ct=<метка>&mt=8` |
| ссылка на Play | `?referrer=utm_campaign%3D<метка>` (percent-encoded!) |
| ссылка на наш сайт | `?utm_campaign=<метка>&utm_source=<канал>` |
| позже — рекламный кабинет | имя кампании ровно этой строкой |

Наш счётчик читает три тега `utm_*` **по имени** и больше ничего из строки запроса; они
попадают в слоты 12-14 и потому доступны в `GROUP BY`.

### Деньги и подписки

### Наши события: середина воронки

Того, что между установкой и оплатой, нет ни у Apple, ни у Google. Это наш счётчик.

| Метрика | Событие | Статус |
|---|---|---|
| Onboarding CVR | `onboarding_completed` ÷ `app_launched` | ждёт клиента в `commonMain` |
| Paywall CVR | `purchase_completed` ÷ `paywall_viewed` | там же |
| R1 / R7 | см. ниже | там же |

**Retention без `DISTINCT`.** Обычный способ — считать уникальных вернувшихся — у нас сломан:
Analytics Engine сэмплирует, выброшенная строка уносит свой `anon`. Поэтому день когорты
считает клиент: приложение знает дату своей установки (оно же сгенерировало UUID) и шлёт
`days_since_install` в `metrics` при каждом запуске.

```
R1 = запуски с days_since_install=1  ÷  запуски с days_since_install=0
```

Отношение **сумм**, а не уникальных, — а суммы взвешиваются через `sum(_sample_interval)` и
сэмплирование переживают. Числитель и знаменатель из одного источника с одинаковым
сэмплированием, поэтому ошибка сокращается. Делить наши запуски на установки Apple нельзя.

### Трафик с роликов

| Метрика | Источник | Статус |
|---|---|---|
| визиты с ролика | наш счётчик, `utm_campaign` | **готово** — метка доезжает |
| клики в стор с ролика | `app_store_opened` + `utm_campaign` | **готово** |
| установки с ролика | ASC Campaigns по тому же `ct` | ждёт фазы 2 |
| просмотры, CTR, удержание ролика | YouTube Analytics API | не начато |

YouTube Analytics API бесплатен для собственного канала (OAuth владельца) и отдаёт просмотры,
показы, CTR и среднюю досмотренность, в том числе для Shorts. Фетчер пишется как `appstore.ts`,
в ту же таблицу с `provider = 'youtube'`. Начинать в день, когда появятся ролики: до этого
писать нечего.

**Ссылку в описании ролика метить обязательно.** Реферер из приложения YouTube часто не
доходит — метка в адресе доходит всегда.

### Реклама — заложено, не построено

| Метрика | Источник | Статус |
|---|---|---|
| Ad Spend | API рекламного кабинета → `provider='<сеть>'`, `metric='ad_spend_usd'` | не начато |
| Paid Installs | ASC Campaigns по `ct` кампании | ждёт фазы 2 |
| CPI | Ad Spend ÷ Paid Installs | — |
| CAC | Ad Spend ÷ New Subscribers | — |
| ROAS / ROI | Revenue ÷ Ad Spend | — |

Таблица к этому готова: место под расход есть, метка кампании общая с органикой, поэтому
платное и бесплатное окажутся в одном отчёте, а не в двух.

**Чего не строим до первой платной кампании:** MMP (AppsFlyer и подобные). Его работа —
третейский суд между рекламными сетями, каждая из которых приписывает установку себе. При
нулевом бюджете он разрешает спор, которого нет. Ставить в день первой кампании.

## Граница

В CLAUDE.md записано: не выращивать это в худший PostHog, никаких воронок и когорт. Эта
таблица формально и есть воронка с когортами, поэтому черта проводится явно:

**Можно** — фиксированный список именованных метрик, считающихся раз в сутки и лежащих
агрегатами. Это табло.

**Нельзя** — интерфейс, где по сырым событиям строят произвольную воронку. Это исследование,
и оно всегда будет хуже PostHog. Если понадобится — направить PostHog на тот же поток.

## Порядок

1. Роль ключа ASC → Admin, vendor number. Разблокирует Sales и Subscription.
2. Фаза 2: Analytics Reports API — Impressions, Page Views, разбивка по `ct`.
3. Отчёты подписок → весь блок Adapty бесплатно.
4. Клиент в `commonMain`: `app_launched` с `days_since_install`, `onboarding_completed`,
   `paywall_viewed`, `purchase_completed`.
5. YouTube — в день первых роликов. Реклама — в день первого бюджета.
