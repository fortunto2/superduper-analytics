# ТЗ: воронка сайт → установка → покупка, и клиент для Kotlin

Разведка и решения. Веб-половина уже сделана (см. ниже), мобильная — нет.

## Чего хотим

Понять, кто пришёл с сайта и поставил приложение, из каких источников приходят, кто заплатил.
Замкнуть цикл продвижения, а не смотреть в две панели, которые никогда не сходятся.

## Чего сделать нельзя, и почему это не компромисс

**Связать конкретного посетителя сайта с конкретной установкой невозможно** — без
кросс-сайтового идентификатора этого не сделать ни у кого, а он запрещён в этом проекте
и делает баннер согласия обязательным. Обходные пути — буфер обмена, отпечаток устройства,
deferred deep links — это и есть тот самый идентификатор под другим именем.

Но эта связь и не нужна. Нужен ответ на вопрос «работает ли лендинг», а он агрегатный.

## Что работает вместо, и уже включено

Ссылка на App Store с сайта несёт **campaign-токен**:

```
https://apps.apple.com/app/apple-store/id6794324877?ct=site-hero&mt=8
```

App Store Connect → Analytics → Acquisition → Campaigns привязывает к этому токену **показы
страницы, установки, продажи и подписки**. Клик по кнопке при этом пишется и у нас как
`app_store_opened`.

Получается цепочка, целиком агрегатная:

| звено | кто считает |
|---|---|
| визит на лендинг | наш счётчик |
| клик на «поставить» | наш счётчик, `app_store_opened` |
| показ страницы в App Store | Apple, по токену |
| установка | Apple, по токену |
| покупка / подписка | Apple, по токену |

Токен помечает **источник**, а не человека. Отсюда и лимит: «с лендинга пришло 40 установок»
— да; «вот этот человек» — нет и не будет.

### Веб: сделано

- **Разные `ct` на разные места** — `site-hero` и `site-footer`, обе кнопки на caretta. Токен
  для Apple и атрибуты для нашего счётчика берутся одной функцией из одного имени места:
  порознь они разъезжаются на первой же новой кнопке.
- **Обработчик кликов уехал в общий сниппет.** `data-sda-event` теперь работает на всех 14
  сайтах без строчки кода на сайте. Бюджет устоял: посетитель платит 893 байта brotli, и тест
  считает именно их, а сырой потолок остался сторожем против копипасты.
- **Проверено на живой странице**, а не на сборке: оба места шлют `app_store_opened` с верным
  `placement`.

### Веб: осталось

- **`pt` (provider token)** из App Store Connect. Без него часть отчётов беднее, `ct` работает
  и так. Берётся вместе с веб-сессией `asc` — см. ниже.
- **Google Play**, когда появится: `referrer` с UTM (обязательно percent-encoded) и Install
  Referrer API. Расписано в скиле `android-release`.

## Мобильная половина: чего нет

Приложение — **Kotlin Multiplatform** (`composeApp/src/commonMain`), не Swift. Сеть уже есть:
`CloudBackend.kt`, `AuthBackend.kt`. Значит клиент пишется один раз в `commonMain` и работает
на iOS и Android сразу — Swift-сниппет из порядка сборки для этого приложения не нужен.

### Что слать

Схема события уже поддерживает мобильные источники: `platform: ios` / `android`, `version`,
`props`, `metrics`. Регистрация есть — `carettafriends`, тот же id, что у сайта, поэтому
визит на лендинг и запуск приложения сравниваются без джойна.

Минимальный набор, которого хватит для воронки:

- `app_launched` с `version`
- `nest_recorded` — то, ради чего приложение существует
- `purchase_completed` с `metrics: { price_usd }`, если появятся покупки

Больше не надо. События дешевле добавить потом, чем убрать из архива.

### `anon` на мобильном: решение

На вебе идентификатор выводится на краю из IP + user-agent и меняется в полночь. **На
мобильном так нельзя** — IP оператора меняется, NAT склеивает абонентов, и «человек» получится
случайным.

Поэтому приложение шлёт **install-scoped UUID**: сгенерирован при первом запуске, лежит
локально, не покидает устройство иначе как в этом поле, и умирает вместе с удалением
приложения. Не IDFA, не device id, не связан с аккаунтом.

Это то, что схема и предполагала (`src/schema.ts`, комментарий к `anon`), и ingest уже
устроен правильно: у `platform != web` побеждает присланный id, у веба — выведенный на краю
(`src/ingest.ts`).

### Развилка, которую надо закрыть до кода

**Декларация в App Store.** Приложение уже ходит в сеть и имеет авторизацию, так что «Data Not
Collected» там наверняка уже не заявлено. Но категорию добавить придётся: события ложатся в
**Product Interaction / Usage Data**, и — при честном UUID выше — в **Data Not Linked to You**.

Проверить действующую декларацию **до** первого релиза со счётчиком — `asc web privacy pull
--app 6794324877`. Нужна веб-сессия Apple: `asc web auth login --apple-id <почта>` с 2FA на
вашем устройстве, без неё ни декларация, ни отчёты по кампаниям не читаются.

Отдельно: ключ ASC API у нас с ролью App Manager, и любой вызов отчётов отвечает 403. Для
`asc analytics` нужна роль с доступом к отчётам (Admin / Finance); либо не расширять ключ и
брать те же числа веб-сессией.
Расхождение метки с поведением — это не мелочь: Apple снимает приложения за это, а у нас
privacy — заявленное свойство продукта, а не строчка в форме.

Заодно обновить privacy-страницу сайта и текст в приложении, если он есть. Правило то же, что
на вебе: счётчик и текст, который его описывает, меняются одним коммитом.

## Порядок сборки

1. `pt` и разные `ct` в ссылках. Ноль кода, работает сразу.
2. Проверить декларацию в App Store Connect. Решить, что заявляем.
3. Клиент в `commonMain`: одна функция, POST на `/e`, батч в памяти, флаш при уходе в фон.
   Сеть уже есть — брать её же, не тянуть новую библиотеку.
4. `app_launched`. Убедиться, что событие видно в `seo traffic` рядом с сайтом.
5. Остальные события по одному.

## Что считать сделанным

В `seo traffic` строка `carettafriends` есть и для `web`, и для `ios`, числа сходятся с App
Store Connect по порядку величины, и на вопрос «окупается ли лендинг» есть ответ из двух
цифр — клики и установки за тот же период.
